# 优化文档

## 一、项目阅读结论

本项目是一个基于 Django + Django REST Framework 的教务管理后端，模块按业务拆分为认证、用户、学生、教师、字典、考试、成绩、仪表盘和 AI 助手。整体架构已经具备以下基础：

- `apps/core` 承载枚举、分页、权限、基础 ViewSet 等跨模块能力。
- `django_edu_manage/common` 统一响应、异常和渲染格式。
- 各业务 CRUD 基本使用 `ViewSet + Serializer + Router`，接口文档使用 `drf-spectacular`。
- 列表接口已部分使用 `select_related`，具备初步性能意识。

本次优化优先选择低风险、高收益、不改变数据库结构和接口响应主形状的点，主要集中在查询性能、筛选参数健壮性、接口行为一致性和日志洁净度。

## 二、已完成优化

### 1. 查询参数校验复用

新增 `apps/core/query_params.py`，提供：

- `get_str_param()`：统一读取并去除字符串查询参数两端空白。
- `get_int_param()`：将 ID 类查询参数转换为整数，非法值抛出 DRF `ValidationError`。
- `get_choice_param()`：校验枚举值是否在 `TextChoices.values` 内。

收益：

- 避免 `?class_id=abc`、`?semester=abc` 这类非法参数直接进入 ORM。
- 参数错误统一进入现有异常处理和统一响应格式。
- 减少多个 ViewSet 中重复的 `.get(...).strip()` 和手写校验逻辑。

### 2. 学生、考试、字典筛选更健壮

已接入参数辅助函数的接口：

- `apps/students/views.py`
  - `grade` 使用 `GradeChoices.values` 校验。
  - `class_id` 转为整数后再过滤。
  - 列表增加 `order_by('id')`，分页顺序更稳定。

- `apps/exam/views.py`
  - `exam_type` 使用 `ExamTypeChoices.values` 校验。
  - `grade` 使用 `GradeChoices.values` 校验。
  - `semester` 转为整数后再过滤。
  - 查询预加载 `semester`，并按 `-exam_date, id` 排序。

- `apps/dicts/views.py`
  - 班级 `grade` 使用枚举校验。
  - 字符串筛选使用统一读取函数。
  - 字典列表增加稳定排序。

### 3. 教师列表消除多对多 N+1

`TeacherProfileSerializer` 会读取：

- `research_groups`
- `research_group_names`
- `class_ids`

原查询只使用了 `select_related('user')`，列表序列化时多对多字段可能按教师逐条查询。

已在 `apps/teachers/views.py` 中补充：

```python
prefetch_related('research_groups', 'class_ids')
```

收益：

- 教师列表页的教研组、任教班级数据一次性预取。
- 教师数量变多时，查询次数更可控。
- 非管理员只看自己数据时同样保留预取和稳定排序。

### 4. 成绩接口补齐已声明筛选能力

`apps/score/views.py` 的接口文档已声明支持：

- `exam`
- `subject`
- `student`
- `grade`
- `class_id`

原实现只处理了前三项。本次补齐：

- `grade`：按 `student__class_id__grade` 筛选。
- `class_id`：按 `student__class_id_id` 筛选。
- `exam`、`subject` 转为整数后再筛选。
- 预加载 `student__class_id`，避免成绩列表访问学生班级链路时额外查询。
- 返回按 `exam_id, student_id, subject_id` 排序。

收益：

- 接口实现和 OpenAPI 文档保持一致。
- 前端按年级、班级查看成绩时无需自行二次过滤。
- 查询参数错误更早、更明确地返回。

### 5. 仪表盘年级分布统计减少查询次数

`apps/dashboard/views.py` 中“全校各年级人数”原逻辑是遍历每个年级并分别 `count()`，会产生多次数据库查询。

已改为一次聚合：

```python
StudentProfile.objects
    .filter(class_id__grade__isnull=False)
    .values('class_id__grade')
    .annotate(count=Count('id'))
```

再按 `GradeChoices.choices` 补齐没有学生的年级。

收益：

- 查询次数从“年级数量 N 次”降低为 1 次聚合查询。
- 返回结构不变，仍包含所有年级，空年级计数为 0。

### 6. 用户审核写入面收窄

`apps/users/views.py` 的审核动作原来调用：

```python
user.save()
```

已改为：

```python
user.save(update_fields=['is_approved', 'is_active'])
```

收益：

- 只更新审核相关字段。
- 减少无关字段写入，降低并发场景下覆盖风险。

### 7. 移除调试输出

`apps/dicts/views.py` 的 `grade_classes()` 中存在：

```python
print('grade_classes: grade_map =', grade_map)
```

已删除。

收益：

- 避免生产或开发服务日志被接口调试信息污染。
- 日志来源更集中到 logging 系统。

## 三、验证结果


结果：

- 本次未进行数据库结构变更，不需要新增 migration。

## 四、后续建议

### 1. 补充接口测试

当前测试套件为空，建议优先补以下用例：

- 学生列表：`grade/class_id` 正常筛选、非法 `class_id` 返回 400。
- 教师列表：断言预取后返回 `research_group_names` 和 `class_ids`。
- 成绩列表：`exam/subject/student/grade/class_id` 组合筛选。
- 仪表盘：无 `grade` 时返回所有年级，指定 `grade` 时返回班级分布。

### 2. 统一查询参数错误消息语言

当前新增辅助函数使用英文错误消息，项目业务消息多为中文。后续可以统一改成中文，例如：

- `class_id 必须是整数`
- `grade 不是有效选项`

### 3. 给高频筛选字段补数据库索引

如果数据量继续增长，建议评估以下字段索引：

- `StudentProfile.stu_no`
- `StudentProfile.realname`
- `TeacherProfile.emp_no`
- `TeacherProfile.realname`
- `ExamPlan.exam_type`
- `ExamPlan.grade`
- `Score.exam`
- `Score.subject`
- `Score.student`

其中外键字段通常已有索引，字符模糊查询是否加索引需结合数据库类型和查询方式评估。

### 4. 统一列表排序策略

本次在视图层为部分列表补了稳定排序。长期可以考虑：

- 简单字典表在 `Meta.ordering` 中声明默认排序。
- 业务表保留视图层排序，避免为排序改模型而产生迁移。
- 大列表支持显式 `ordering` 参数，并限制可排序字段。

### 5. 清理未使用 import 和空测试文件

部分模块仍有模板生成的空测试文件或未使用 import。建议引入 `ruff` 或类似工具做自动检查，避免人工维护成本。
